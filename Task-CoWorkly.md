# Техническое задание

**Проект:** CoWorkly — сервис бронирования рабочих мест и переговорных комнат
**Тип:** внутренняя система для коворкинга
**Версия документа:** 1.0

---

## 1. Назначение системы

Система предназначена для управления бронированием рабочих мест (десков) и переговорных комнат в коворкинге: регистрация пользователей, просмотр доступности, создание и отмена броней, администрирование пространств и тарифов.

---

## 2. Роли пользователей

| Роль | Права |
|---|---|
| Гость | регистрация, авторизация |
| Пользователь | просмотр доступности, создание брони, просмотр своих броней, отмена брони |
| Администратор | CRUD рабочих пространств, CRUD тарифов, просмотр всех броней, блокировка пользователей |

---

## 3. Функциональные требования

### 3.1 Пользователи
- FR-1.1: Регистрация по email и паролю. Пароль хранится в виде хэша (bcrypt/argon2), не в открытом виде.
- FR-1.2: Авторизация по email/паролю, выдача токена доступа.
- FR-1.3: Администратор может заблокировать пользователя (`is_blocked = true`); заблокированный пользователь не может создавать новые брони.

### 3.2 Рабочие пространства
- FR-2.1: Пространство имеет тип: `DESK` (одно место, вместимость всегда 1) или `MEETING_ROOM` (вместимость от 2 до N, задаётся администратором).
- FR-2.2: Администратор может создавать, редактировать, деактивировать пространства.
- FR-2.3: Деактивированное пространство не отображается в списке доступных для бронирования, но сохраняет историю броней.

### 3.3 Бронирование
- FR-3.1: Пользователь может получить список свободных пространств на заданный интервал времени (дата, время начала, время окончания).
- FR-3.2: Пользователь может создать бронь, указав пространство, интервал времени и (для переговорной) количество участников.
- FR-3.3: Система обязана отклонять бронь, если интервал пересекается с уже существующей активной бронью того же пространства.
- FR-3.4: Система обязана отклонять бронь переговорной комнаты, если количество участников превышает вместимость пространства.
- FR-3.5: Пользователь может отменить свою бронь.
- FR-3.6: Отмена брони менее чем за 3 часа до её начала фиксируется отдельным статусом (`LATE_CANCELLED`), отличным от обычной отмены (`CANCELLED`).
- FR-3.7: Бронь, время начала которой прошло, а статус остался `PENDING_PAYMENT` (не подтверждена), автоматически переводится в статус `EXPIRED` не позднее, чем через 5 минут после наступления времени начала.
- FR-3.8: Администратор может просматривать список всех броней с фильтрацией по пользователю, пространству, дате, статусу.

### 3.4 Тарификация
- FR-4.1: Стоимость брони рассчитывается по формуле: `базовая_ставка_пространства × длительность_в_часах × коэффициент_дня`.
- FR-4.2: Коэффициент дня зависит от того, будний это день или выходной, и задаётся в справочнике тарифов, а не хардкодится.

### 3.5 Экспорт
- FR-5.1: Пользователь может выгрузить список своих броней в файл формата CSV за произвольный период.

---

## 4. Бизнес-правила (инварианты)

- BR-1: Не может существовать двух активных (`CONFIRMED`) броней одного пространства с пересекающимися интервалами времени.
- BR-2: Проверка пересечения и создание брони должны выполняться как единая атомарная операция (недопустима гонка, при которой два пользователя одновременно бронируют один и тот же слот).
- BR-3: Количество участников брони переговорной комнаты не может превышать её вместимость.
- BR-4: Стоимость брони, однажды рассчитанная и сохранённая, не пересчитывается задним числом при изменении тарифов.

---

## 5. Нефункциональные требования

- NFR-1: Хранилище данных — PostgreSQL.
- NFR-2: Схема БД версионируется миграциями (Flyway), ручные изменения схемы в обход миграций запрещены.
- NFR-3: Бизнес-логика (расчёт тарифа, проверка пересечений) покрыта unit-тестами.
- NFR-4: Логирование ключевых операций (создание/отмена брони, блокировка пользователя) через SLF4J.
- NFR-5: Все SQL-запросы с пользовательскими данными выполняются через параметризованные запросы (`PreparedStatement`), конкатенация строк в SQL запрещена.
- NFR-6: Пароли пользователей никогда не логируются и не возвращаются в API-ответах.

## 6. Модель данных (минимальная)

```
users
  id            BIGSERIAL PK
  email         TEXT UNIQUE NOT NULL
  password_hash TEXT NOT NULL
  full_name     TEXT NOT NULL
  role          TEXT NOT NULL          -- USER | ADMIN
  is_blocked    BOOLEAN NOT NULL DEFAULT false
  created_at    TIMESTAMP NOT NULL DEFAULT now()

workspaces
  id           BIGSERIAL PK
  type         TEXT NOT NULL           -- DESK | MEETING_ROOM
  name         TEXT NOT NULL
  capacity     INT NOT NULL
  hourly_rate  NUMERIC(10,2) NOT NULL
  is_active    BOOLEAN NOT NULL DEFAULT true

tariffs
  id              BIGSERIAL PK
  workspace_type  TEXT NOT NULL
  day_type        TEXT NOT NULL        -- WEEKDAY | WEEKEND
  multiplier      NUMERIC(4,2) NOT NULL

bookings
  id                  BIGSERIAL PK
  user_id             BIGINT FK -> users.id
  workspace_id        BIGINT FK -> workspaces.id
  start_time          TIMESTAMP NOT NULL
  end_time            TIMESTAMP NOT NULL
  participants_count  INT NOT NULL DEFAULT 1
  status              TEXT NOT NULL     -- PENDING_PAYMENT | CONFIRMED | CANCELLED | LATE_CANCELLED | EXPIRED
  price               NUMERIC(10,2) NOT NULL
  created_at          TIMESTAMP NOT NULL DEFAULT now()
```

Обязательный индекс: `(workspace_id, start_time, end_time)`.

## 7. Интерфейс на этапе 1 (консольное приложение)

Взаимодействие через консольное меню, без графического интерфейса и без REST API. Минимальный набор команд:

1. Зарегистрировать пользователя
2. Войти
3. Показать свободные пространства на дату/интервал
4. Создать бронь
5. Показать мои брони
6. Отменить бронь
7. [ADMIN] Показать все брони с фильтрами
8. [ADMIN] Создать/деактивировать пространство
9. Экспорт моих броней в CSV

---

## 8. Вне рамок этапа 1 (Out of scope)

- Реальная оплата (платежи мокируются/пропускаются).
- Веб-интерфейс, REST API, JavaFX-клиент — реализуются на последующих этапах.
- Email/push-уведомления.
- Многоязычность.

---

## 9. Критерии приёмки

- Все пункты раздела 3 (FR) реализованы и проверяются вручную через консольное меню.
- Все пункты раздела 4 (BR) покрыты автотестами, тесты проходят.
- Попытка одновременного бронирования одного и того же слота двумя потоками не приводит к двойной брони (проверяется тестом с параллельным выполнением).
- Схема БД создаётся исключительно через миграции Flyway из чистой базы.
- Код собирается командой `mvn clean install` без ошибок, все тесты зелёные.
